Oct 25: Built a sketch (mpu_accel_x) that reads ACCEL_XOUT_H and ACCEL_XOUT_L from the MPU-6050, glues them into one number and prints it to the Serial Monitor. I predicted X would be about 0 with the board lying flat. It actually read between -1520 and -1700, and it never held one value, so a still board gives a noisy number. The first run printed about 63800 because int is 32 bits, so it can hold negatives, but two glued bytes only give 0 to 65535, so a reading of -1736 showed up as 63800, and int16_t fixed it. Holding the X arrow up and down gave about +17200 and -15236, so roughly 16200 counts per g. I learned how the sensor reads constant gravity and saw live data from it for the first time. Then I extended it to mpu_all_axes, which reads all 14 bytes from 0x3B and prints seven values: acceleration, temperature and gyro. On a flat board I predicted Z would be about -16000 and Y would match X, but it read X -1620, Y -632 and Z +17352, so Z is large and positive and Y is different. Temperature comes out near 24 C with raw/340 + 36.53 (not checked in the datasheet), and my fingertip test lowered it by 230 counts, which I can't explain. Still gyros bounce by 5 to 30 counts, and turning the board by hand gave gz down to -15350. With the logic analyzer on SCL and SDA, one 14-byte read took about 1633 us, against the 1530 us I predicted. The decoder showed address 68, register 3B, a repeated start (my endTransmission(false)), address read 68, the data bytes, then a NACK and a stop.

Oct 26: Added a marker pin on P4 that goes high during one pass of the code and low during the delay, and watched it on the analyzer. One pass takes about 2.15 ms and the period was 202.007 ms, found with a script that reads every pulse from the capture file. Cutting the delay from 200 to 198 gave a period of 200.005 ms, which matches my guess of work plus delay. The gaps never differed by more than 0.05 ms, which is the smallest step the analyzer shows at 20 kHz. My first capture stopped early and held only 8 pulses, and my cursor span for it was off by 1.5 ms, so I trust the script more than the cursors.

Oct 29: Today I changed the code scheduling by tracking a next_due time instead of a fixed delay. I guessed 200 ms, but the fixed-delay sketch with extra work measured 203.005 ms against Monday's 200.005 ms baseline, while the clock sketch with the same extra work measured 200.006 ms, leaving capture 4 saved but unanalyzed. The pulse width grew from 2.15 to 5.0 ms, with 203.005 and 200.006 being periods. They differ because fixed delay waits a set time after work to hit 203 ms, whereas the clock sketch waits until next_due so wait time shrinks when work grows.
